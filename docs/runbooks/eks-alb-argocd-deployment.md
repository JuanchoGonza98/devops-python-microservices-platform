# Runbook: AWS EKS Deployment with ALB Ingress and Argo CD

---

## 1. Overview

This runbook documents the end-to-end process for provisioning and operating the AWS EKS deployment environment for the `devops-python-microservices-platform`.

It covers infrastructure provisioning with Terraform, EKS cluster setup, installation of the AWS Load Balancer Controller, ALB-based ingress exposure, and Argo CD as the GitOps engine.

### End-to-end flow

```
Terraform
  └─> VPC + Public Subnets (with EKS/ALB tagging)
        └─> EKS Cluster + Managed Node Group
              └─> Base add-ons: vpc-cni / coredns / kube-proxy
                    └─> AWS Load Balancer Controller (Helm + IRSA)
                          └─> ALB Ingress (gateway-ingress.yaml)
                                └─> Argo CD (GitOps)
                                      └─> App deployed in namespace devops-platform
```

### Note on the active overlay

The active overlay for deployment on AWS EKS is **`deploy/kubernetes/overlays/dev`**. This overlay uses images published to GHCR with `ci-<sha>` tags generated by the CI pipeline. The `prod` overlay is not active in this environment.

## 4. Terraform Variable Configuration

The environment configuration is managed through the `terraform.tfvars` file located in `infra/terraform/environments/portfolio/`.

### Reference template

The file `terraform.tfvars.example` serves as the starting point:

```hcl
cluster_version = "1.33"

cluster_endpoint_public_access_cidrs = [
  "YOUR_PUBLIC_IP/32"
]

node_instance_types = ["t3.medium"]
node_desired_size   = 1
node_min_size       = 1
node_max_size       = 2
```

### Creating the actual file

```bash
cp infra/terraform/environments/portfolio/terraform.tfvars.example \
   infra/terraform/environments/portfolio/terraform.tfvars
```

Edit `terraform.tfvars` replacing the placeholders with real values:

```hcl
cluster_version = "1.33"

cluster_endpoint_public_access_cidrs = [
  "203.0.113.42/32"   # <-- replace with the operator's actual public IP
]

node_instance_types = ["t3.medium"]
node_desired_size   = 1
node_min_size       = 1
node_max_size       = 2
```

> **Warning:** Replacing `YOUR_PUBLIC_IP/32` with the actual public IP of the operator is mandatory. Without this, access to the cluster API server will be blocked. Verify the current public IP with `curl https://checkip.amazonaws.com`.

> **Reminder:** `terraform.tfvars` **must never be committed**. Confirm it is in `.gitignore` before proceeding.

Work from the environment directory:

```bash

```

```bash

```

### Format and validate

```bash

```

```bash
terraform plan
```

Review the plan before applying. Pay special attention to:
- Access CIDRs for the API server.
- Node group instance type and size.
- That `desired_size >= min_size`.

### Apply

```bash

```

Confirm with `yes` when prompted. The process can take between 10 and 20 minutes.

- **VPC** with CIDR `10.30.0.0/16` and DNS enabled.

- **Managed Node Group** with `t3.medium` ON_DEMAND instances.
- **EKS add-ons**: `vpc-cni`, `coredns`, `kube-proxy`.

  --cluster-name YOUR_CLUSTER_NAME \
  --addon-name vpc-cni \

### Note on provisioning order

During the construction of this environment it was observed that if add-ons (`vpc-cni`, `coredns`, `kube-proxy`) are not available before nodes start, the managed node group can enter a failed state with `NodeCreationFailure` errors. The EKS module in this repository defines `vpc-cni` with `before_compute = true`, ensuring the network plugin is active before nodes register. If working with a cluster created outside this module, add-ons must be installed manually before adding nodes.

## 8. Subnet Tagging for ALB

The AWS Load Balancer Controller requires public subnets to be correctly tagged in order to provision `internet-facing` ALBs.

The VPC module in this repository applies these tags automatically on the `aws_subnet.public` resource:

```hcl
"kubernetes.io/role/elb"                    = "1"
"kubernetes.io/cluster/${var.cluster_name}" = "shared"
```

If for any reason these tags need to be applied manually (e.g., on existing subnets not managed by Terraform):

```bash
aws ec2 create-tags \
  --resources subnet-XXXXXXXXXXXXXXXXX subnet-YYYYYYYYYYYYYYYYY \
  --tags \
    Key=kubernetes.io/role/elb,Value=1 \
    Key=kubernetes.io/cluster/YOUR_CLUSTER_NAME,Value=shared \
  --region YOUR_REGION
```

Verify the applied tags:

```bash
aws ec2 describe-subnets \
  --subnet-ids subnet-XXXXXXXXXXXXXXXXX \
  --query 'Subnets[*].Tags' \
  --region YOUR_REGION
```

## 9. AWS Load Balancer Controller Installation

The AWS Load Balancer Controller reconciles Kubernetes `Ingress` resources into real AWS ALBs. It requires specific IAM permissions via IRSA (IAM Roles for Service Accounts).

### 9.1 Verify the cluster OIDC provider

```bash
aws eks describe-cluster \
  --name YOUR_CLUSTER_NAME \
  --region YOUR_REGION \
  --query "cluster.identity.oidc.issuer" \
  --output text
```

If no OIDC provider is associated, create one:

```bash
eksctl utils associate-iam-oidc-provider \
  --cluster YOUR_CLUSTER_NAME \
  --region YOUR_REGION \
  --approve
```

### 9.2 Download the official IAM policy

```bash
curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.7.2/docs/install/iam_policy.json
```

### 9.3 Create the IAM policy in AWS

```bash
aws iam create-policy \
  --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json \
  --region YOUR_REGION
```

### 9.4 Create the service account with IRSA

```bash
eksctl create iamserviceaccount \
  --cluster YOUR_CLUSTER_NAME \
  --namespace kube-system \
  --name aws-load-balancer-controller \
  --role-name AmazonEKSLoadBalancerControllerRole \
  --attach-policy-arn arn:aws:iam::YOUR_AWS_ACCOUNT_ID:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve \
  --region YOUR_REGION
```

> **Why IRSA:** Allows the controller pod to assume a specific IAM role without static credentials. The service account is annotated with the IAM role ARN and the cluster uses the OIDC provider to validate the identity.

### 9.5 Install via Helm

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  --namespace kube-system \
  --set clusterName=YOUR_CLUSTER_NAME \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=YOUR_REGION \
  --set vpcId=YOUR_VPC_ID
```

### 9.6 Validate the deployment

```bash
kubectl get deployment -n kube-system aws-load-balancer-controller
kubectl get pods -n kube-system -l app.kubernetes.io/name=aws-load-balancer-controller
```

Both pods must be in `Running` state. If any remain in `Pending` or `CrashLoopBackOff`, check the logs:

```bash
kubectl logs -n kube-system \
  -l app.kubernetes.io/name=aws-load-balancer-controller \
  --tail=50
```

## 12. ALB Ingress Exposure

### Ingress manifest

The ALB Ingress is defined in `deploy/kubernetes/overlays/dev/gateway-ingress.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: gateway-alb
  namespace: devops-platform
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80}]'
    alb.ingress.kubernetes.io/healthcheck-path: /health
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: gateway
                port:
                  number: 8080
```

**Annotation details:**

| Annotation | Value | Description |
|---|---|---|
| `scheme` | `internet-facing` | ALB accessible from the internet |
| `target-type` | `ip` | Traffic goes directly to pod IPs (requires `vpc-cni`) |
| `listen-ports` | `[{"HTTP":80}]` | HTTP listener on port 80 |
| `healthcheck-path` | `/health` | Path used by the ALB to verify target health |

The Ingress is applied together with the overlay (`kubectl apply -k deploy/kubernetes/overlays/dev`). No separate apply is required.

### Get the ALB hostname

```bash
kubectl get ingress -n devops-platform
kubectl get ingress gateway-alb -n devops-platform \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'
```

The ALB hostname may take 2–5 minutes to appear after Ingress creation.

### Validate the Ingress

```bash
kubectl describe ingress gateway-alb -n devops-platform
```

Verify that the `Address` field contains a valid hostname and that no controller errors appear in the events.

### Validate HTTP access

```bash
# Replace ALB_HOST with the hostname obtained above
curl http://ALB_HOST/health
curl -I http://ALB_HOST/
curl http://ALB_HOST/products
curl http://ALB_HOST/users
```

> **Important:** The validated access in this environment is exclusively via **HTTP (port 80)**. HTTPS is not configured in this flow — there is no port 443 listener or ACM certificate associated with the ALB. Do not assume HTTPS is available.

## 14. Troubleshooting

### NodeCreationFailure in the managed node group

**Symptom:** The node group enters `CREATE_FAILED` or `DEGRADED` state. Nodes do not appear in `kubectl get nodes`.

**Common cause:** Network add-ons (especially `vpc-cni`) were not available before the node group attempted to register nodes. Can also occur due to scaling configuration inconsistencies (`min_size > desired_size`).

**Actions:**
```bash
aws eks describe-nodegroup \
  --cluster-name YOUR_CLUSTER_NAME \
  --nodegroup-name default \
  --region YOUR_REGION \
  --query 'nodegroup.health'

# Verify add-ons
aws eks list-addons --cluster-name YOUR_CLUSTER_NAME --region YOUR_REGION

# Verify that desired_size >= min_size in terraform.tfvars
terraform plan
```

---

### CNI plugin not initialized

**Symptom:** Nodes appear as `NotReady`. Describing the node shows `CNI plugin not initialized`.

**Cause:** The `vpc-cni` add-on is not installed or has not finished initializing.

**Actions:**
```bash
aws eks describe-addon \
  --cluster-name YOUR_CLUSTER_NAME \
  --addon-name vpc-cni \
  --region YOUR_REGION \
  --query 'addon.status'

# If not present, create it
aws eks create-addon \
  --cluster-name YOUR_CLUSTER_NAME \
  --addon-name vpc-cni \
  --region YOUR_REGION
```

---

### Missing add-ons: vpc-cni / coredns / kube-proxy

**Symptom:** `kubectl get pods -n kube-system` shows CoreDNS pods in `Pending` or absent. Nodes cannot resolve internal DNS.

**Actions:**
```bash
aws eks list-addons --cluster-name YOUR_CLUSTER_NAME --region YOUR_REGION

# Create missing add-ons
aws eks create-addon --cluster-name YOUR_CLUSTER_NAME --addon-name coredns --region YOUR_REGION
aws eks create-addon --cluster-name YOUR_CLUSTER_NAME --addon-name kube-proxy --region YOUR_REGION
```

---

### ImagePullBackOff due to incorrect image tags

**Symptom:** Pods fail to start. `kubectl describe pod` shows `Failed to pull image`.

**Cause:** The overlay references images that do not exist in the registry or that the cluster cannot access.

**Actions:**
```bash
kubectl describe pod <pod-name> -n devops-platform | grep -A5 "Events"

# Check the image tag configured in the overlay
cat deploy/kubernetes/overlays/dev/kustomization.yaml | grep newTag
```

Ensure the `dev` overlay is being used, not `prod`.

---

### Argo CD port-forward fails

**Symptom:** `kubectl port-forward` does not respond or the connection is refused.

**Cause:** The `argocd-server` pod is not in `Running` state.

**Actions:**
```bash
kubectl get pods -n argocd
kubectl describe pod argocd-server-XXXXXXXXX -n argocd
kubectl get events -n argocd --sort-by='.lastTimestamp'
```

Resolve the pod state before attempting the port-forward.

---

### ALB created but no response or 502/504 errors

**Symptom:** The ALB hostname exists but HTTP requests fail or return errors.

**Common causes:**
- Targets are `unhealthy` (healthcheck on `/health` does not respond).
- The ALB security group does not allow inbound traffic from the internet.
- The gateway pod is not `Running`.

**Actions:**
```bash
# Verify ALB status
aws elbv2 describe-load-balancers --region YOUR_REGION

# Verify listeners
aws elbv2 describe-listeners \
  --load-balancer-arn YOUR_ALB_ARN \
  --region YOUR_REGION

# Verify target health
aws elbv2 describe-target-health \
  --target-group-arn YOUR_TARGET_GROUP_ARN \
  --region YOUR_REGION

# Verify the gateway pod
kubectl get pods -n devops-platform -l app=gateway
kubectl logs -n devops-platform -l app=gateway --tail=50
```

---

### Terraform error: min_size > desired_size

**Symptom:** `terraform apply` fails with an error related to node group scaling inconsistencies.

**Cause:** `node_min_size` is greater than `node_desired_size` in `terraform.tfvars`.

**Fix:** Ensure `desired_size >= min_size`:

```hcl
node_desired_size = 1
node_min_size     = 1
node_max_size     = 2
```

## 15. Security and Best Practices

- **Do not commit `terraform.tfvars`**: It contains access CIDRs and sensitive configuration. It is in `.gitignore`. Use `terraform.tfvars.example` as the versioned reference.
- **Do not hardcode real IPs in documentation**: Use placeholders like `YOUR_PUBLIC_IP/32` in any versioned file.
- **Do not expose access keys**: Use IAM roles or credential profiles. Never commit `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`.
- **Principle of least privilege**: The Load Balancer Controller IAM policy is scoped to the actions it needs. Do not expand permissions without justification.
- **IRSA over static credentials**: The controller uses IRSA (IAM Roles for Service Accounts) to authenticate with AWS. Do not inject credentials as environment variables or manual secrets.
- **Separate dev/prod**: The `dev` overlay uses `ci-<sha>` images suited for fast iteration. A production environment requires a dedicated overlay with semantic versioned images and additional quality gates.
- **HTTPS pending**: The ALB in this environment only exposes port 80. For any use beyond development or demonstration, HTTPS must be configured with an ACM certificate and a port 443 listener.

## 16. Next Steps

The following improvements are the natural path to mature this environment:

- **HTTPS with ACM**: Create a certificate in AWS Certificate Manager and configure a port 443 listener on the ALB. Update the Ingress with the `alb.ingress.kubernetes.io/certificate-arn` annotation.
- **Custom domain**: Associate a DNS domain with the ALB hostname via a CNAME record, or use `external-dns` to automate DNS management.
- **Strict dev/prod separation**: Create a `prod` overlay with versioned images, production replica counts, and appropriate resource requests/limits.
- **Automated Argo CD bootstrap**: Manage the Argo CD installation via an App of Apps pattern or Helm chart, instead of a manual apply.
- **CI/CD pipeline updating the overlay**: Integrate a step in the CI pipeline that automatically updates the image tag in the corresponding overlay's `kustomization.yaml` after each successful build.
- **Terraform + GitOps integration**: Manage supporting infrastructure resources (namespaces, RBAC, CRDs) via Argo CD where appropriate.
- **external-dns**: Automate the creation and update of Route 53 DNS records from cluster Ingress resources.
- **Observability**: Integrate metrics (Prometheus + Grafana), centralized logging (Fluent Bit + CloudWatch or equivalent), and distributed tracing.
- **Secrets management**: Migrate Kubernetes secrets to AWS Secrets Manager or HashiCorp Vault, integrated via the External Secrets Operator.
